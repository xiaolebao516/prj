# 检验流程架构评审

> 前提：学长经过大量实验验证，严格检验才能使测量结果与样机一致。以下评审不预设"严格 = 有问题"的立场，而是从管线结构本身出发，审视设计上是否存在可改进之处。

---

## 一、管线全景

```
                    ┌──────────┐
   每帧(80ms)  →   │ 帧级 7 闸 │ → strictValid? ──YES──→ 攒够30帧 → 计算本轮均值
                    └──────────┘        │
                                   NO   │
                                    ↓   │
                                   丢弃  │
                                        ↓
                              ┌─────────────────┐
                              │ 轮级质量检查      │
                              │ corrA/corrB/angle│ → 通过? ──YES──→ 加入 candidateRoundList
                              └─────────────────┘       │
                                                   NO   │
                                                    ↓   │
                                              本轮作废    │
                                              重新测量    │
                                                        ↓
                                              ┌──────────────────┐
                                              │ 最终轮次聚类      │
                                              │ ±180 m/s, ≥3轮  │ → 截尾均值 → 最终SOS
                                              └──────────────────┘
```

三层过滤：帧级 → 轮级 → 最终聚类。每一层都会淘汰数据。

---

## 二、结构层面的观察

### 观察 1：闸门之间存在逻辑包含关系

```
diffOk:       abs(lagA - lagB) <= 18
angleSignedDiffOk:  lagA - lagB ∈ [7, 13]
```

`angleSignedDiffOk` 是 `diffOk` 的**严格子集**。当 `enablePatientAngleGate = true` 时，`diffOk` 在逻辑上完全冗余——任何通过 `angleSignedDiffOk` 的帧必然通过 `diffOk`。

这不是 bug（可能是历史遗留，或者作为 `enablePatientAngleGate = false` 时的后备），但如果 `enablePatientAngleGate` 始终为 `true`，可以考虑合并，减少概念上的复杂度。

**结论**：不影响正确性，但说明管线是在迭代中逐步叠加的，存在清理空间。

---

### 观察 2：stableOk 的"锁定中心"可能并非最优角度

`stableOk` 的锁定机制是：取 warmup 窗口中 lagB 的**中位数**作为锁定中心。这意味着它锁定的是"操作者停留最久的那个角度"，而不是"生理上正确的角度"。

如果操作者恰好在一个偏差角度上停留了足够久，系统会锁定在那个偏差角度上，后续只接受与偏差角度一致的帧。此时最终 SOS 会系统性偏离真实值，但因为内部一致性高（所有帧都在同一偏差角度），系统不会报警。

**这不是参数松紧的问题，而是机制本身缺少一个"该角度对应的 SOS 是否合理"的验证**。

可能的改进方向（不改变现有参数）：
- 锁定后检查该角度下的 SOS 是否在桡骨合理区间内（例如 3600~4200 m/s）
- 如果偏离过大，提示操作者调整角度后重新锁定

---

### 观察 3：单通道稳定性 ≠ 双通道姿态稳定性

当前设计只追踪 `lagB` 的稳定性。但姿态门控用的是 `signedLagDiff (lagA - lagB)` 和 `pairMidGap`。如果操作者保持了 lagB 极其稳定，但 lagA 在波动（例如因为 A 对探头接触压力变化），那么：

- `stableOk = true`（lagB 稳定）
- 但 `angleOk = false`（signedLagDiff 频繁越界）
- 进度条仍然不动

操作者的体验会是："系统明明显示锁定/LOCKED，为什么还是采不到有效值？"

**这不是参数松紧的问题**，而是稳定性的监控对象（lagB）和姿态判定的依赖对象（lagA - lagB）不一致导致的**信息不对称**。操作者看到的"锁定"指示灯并没有真实反映姿态是否 OK。

---

### 观察 4：轮级质量检查是"全有或全无"的二级淘汰

即使 30 帧全部通过了严苛的帧级 7 闸，这一轮仍然可能在轮级被淘汰：

```
if (oneRoundCorrB < 0.55 || oneRoundCorrA < 0.80 || !oneRoundAngleOk) {
    // 整轮 30 帧全部作废，过程归零，采集停止
}
```

这意味着操作者花了数秒攒够 30 帧后，可能被告知"本轮无效，请重新调整探头"。从用户体验角度，这是最打击信心的环节。

**潜在的改进**：与其在轮结束时做硬性淘汰，不如在轮进行中就实时提示"当前轮平均 corrA/angle 偏低，建议微调探头"。让操作者在采集过程中就能感知到质量趋势并做出调整，而不是在最后才被告知失败。

---

### 观察 5：帧级检验参数的标定样本可能不够广

代码注释显示，`angleSignedDiff` 和 `anglePairMidGap` 的范围来自一组 CSV 实验：

```
// 3600 错误角度：signedLagDiff≈5,  pairMidGap≈27
// 3800 正确角度：signedLagDiff≈10, pairMidGap≈6.5
// 4000 错误角度：signedLagDiff≈1,  pairMidGap≈-4.5
```

这是**在特定个体上、用特定探头角度**测得的三组数据。问题是：

- 不同人的桡骨粗细、曲率、皮质骨厚度差异很大
- 同一个人的 SOS 在桡骨不同位置（近端/远端）天然不同
- 如果标定对象恰好 SOS=3800，且 signedLagDiff=10，那么 SOS=3700 的骨质疏松患者在同一探头上可能天然就 signedLagDiff=8 或 6

**如果参考样机没有这个问题**，那可能是因为样机使用了更鲁棒的角度估计方法（比如直接测量探头倾角），而不是从超声信号中间接推算。

---

### 观察 6：二值门控 vs 连续置信度

所有 7 个闸门都是**二值判断**（通过/不通过）。没有"置信度"或"软判决"的概念。

- 一个帧如果 `signedLagDiff = 6.9` 被拒，`7.0` 通过——这 0.1 的差异在物理上没有意义
- 而一个帧如果 `signedLagDiff = 13.1` 被拒，`12.9` 通过——同样没有物理意义

二值门控在硬件触发（如波包跳变检测）上是合适的。但在连续物理量（如角度估计）上，使用**加权置信度**可能更合理——给"刚好在边界内"的帧较低的权重，而不是直接拒绝。

当然，如果在严格的二值门控下已经和样机对齐了，这说明二值门控确实做到了有效筛选。问题在于：是否存在大量"在边界附近"的帧本可以贡献有效信息却被丢弃？

## 三、可能存在的实际问题（非参数层面）

### 问题 1：`angleOk` 的两项之间存在信息重叠

`signedLagDiff` 和 `pairMidGap` 都来自同一组 onset 点：

```
signedLagDiff = (aRes.lateOnset - aRes.earlyOnset) - (bRes.lateOnset - bRes.earlyOnset)
pairMidGap    = 0.5*(bRes.earlyOnset + bRes.lateOnset) - 0.5*(aRes.earlyOnset + aRes.lateOnset)
```

这两者不是独立的——它们从同一组 4 个 onset 点推导出来。当 onset 检测出现误差时，两个指标会**同时漂移**，而不是独立验证。

这就像用同一把尺子量了两次然后说"两次结果一致所以测量准确"——它们的一致性是必然的，不是额外的验证。

**如果学长发现两个条件同时启用才能匹配样机**，可能不是因为两个条件各自贡献了独立信息，而是因为组合后的有效窗口更窄（交集效应），恰好筛掉了样机认为无效的帧。如果是这样，可以考虑用一个更精心设计的单一指标替代两个指标。

---

### 问题 2：轮间 `stableOk` 状态不重置的不一致性

`stableOk` 的状态（`boneLagLocked`、`lockedBoneLagCenter`）在轮之间**不重置**。它只在以下情况重置：
- `stopPatientMeasurement()` 调用 `resetBoneLagStability()`
- 但每轮结束后恰恰调用的是 `stopPatientMeasurement()`

所以实际上每轮结束后 stable 状态是重置的。但如果将来有人改了停止/重启逻辑，这一块可能产生 bug —— 新的一轮继承了旧的锁定中心。

这只是潜在的维护风险，不是当前 bug。

---

### 问题 3：`processValidTarget = 30` 是否必要？

每轮需要攒 30 个有效帧。自动触发 80ms 一次，理想情况下 30×80ms = 2.4 秒完成一轮。加上预热等待，一轮大约需要 4~6 秒。

截尾均值已经去掉了 20% 的极端值（30×0.2=6 个），剩下的 24 个做平均。统计上，24 个样本对 SOS 这种慢变量（人体不动的话 SOS 基本恒定）来说已经足够。30 这个数字本身不是问题。

但如果你想要加快测量节奏，可以考虑 20 帧 + 截尾均值 0.2（保留 16 帧平均），在精度损失极小的情况下缩短每轮时间。

## 四、总结：管线的优势与局限

### 设计得好的地方

| 机制 | 评价 |
|------|------|
| 三层过滤（帧→轮→最终聚类） | ✅ 结构合理，每一层解决不同粒度的问题 |
| `bJumpOk` 波包跳变检测 | ✅ 针对具体物理问题（选错波包），阈值设计合理 |
| 轮级聚类（`findBestRoundCluster`） | ✅ 即使有离群轮也不影响最终结果，是很好的兜底 |
| 截尾均值（trimmedMean 20%） | ✅ 抗个别异常帧的干扰 |
| 姿态门控的设计思想 | ✅ 方向正确——探头角度确实影响 SOS |

### 有改进空间的地方

| 观察 | 严重程度 | 说明 |
|------|----------|------|
| `angleSignedDiff` 和 `diffOk` 逻辑包含 | 低 | 不导致 bug，但增加理解负担 |
| 锁定中心可能偏向操作者习惯而非生理正确 | 中 | 建议加 SOS 合理性检查 |
| `stableOk` 只追踪 lagB 但 angleOk 依赖 lagA | 中 | 操作者看到"锁定"但帧仍然被拒 |
| `signedLagDiff` 和 `pairMidGap` 信息重叠 | 中 | 两个指标并非独立验证 |
| 轮级淘汰是"全有或全无" | 中 | 建议增加轮进行中的质量提示 |
| 标定样本可能不够广 | 低-中 | 取决于学长做实验的受试者数量和多样性 |
| 预热期无反馈 | 低 | 纯 UI 问题，但严重影响操作者信心 |

### 不认为是问题的地方

- **`bJumpOk` 的 70 阈值**：合理，基于明确的物理依据（波包跳变特征）
- **`notBoundary` 的 260 阈值**：非常宽松，不会误伤
- **7 闸 AND 链本身**：如果每个闸都捕捉独立的失效模式，AND 链是正确的。上面指出的问题是闸之间的依赖关系，不是 AND 的数量
- **学长的实验结论**：严格检验确实提高了与样机的一致性——这不是偶然。管线的核心思想是正确的，只是个别机制可以更精确

---

## 五、如果要改动，建议的改进路径

从"对测量精度影响最小、对用户体验改善最大"排序：

1. **加 debug 日志分析，不急着改参数**  
   在实际人体测量时采集 `PatientValidCheck` 的所有字段，统计 7 个闸门各自的**拒绝率**。找到真正的瓶颈闸门。数据驱动，不猜。

2. **轮进行中增加质量提示**（不改任何检验逻辑）  
   在 `updateProcessPanel` 中显示当前积累帧的平均 corrA/corrB/signedLagDiff，让操作者在采集过程中就能感知趋势、主动调整。

3. **考虑将 `angleSignedDiff` 和 `pairMidGap` 合并为一个角度指标**  
   因为它们不是独立的（来自同一组 onset），合并后只需维护一个窗口参数，减少调参复杂度。

4. **验证 `stableOk` 锁定的角度是否合理**  
   在锁定后打印该角度的 SOS，确认它在桡骨合理范围内。这不需要改参数，只需加一行 log。

这些改进不会降低检验的严格性，但会让系统的行为更加透明、可诊断。
